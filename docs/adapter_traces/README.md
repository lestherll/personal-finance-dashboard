# Adapter pipeline traces

Concrete, checked-in JSON showing exactly what happens to a bank statement
as it moves through Bronze → Silver, one representative transaction at a
time. `CLAUDE.md` describes each layer in prose; these files show it
happening to real values, generated by actually running the ingestion +
Silver pipeline against a synthetic-but-structurally-faithful fixture (not
hand-written by inspection).

Each `<source_type>.json` traces every transaction through:

1. `stage_1_parsed_transaction` — what `adapter.parse_transactions()` extracts from the raw statement text
2. `stage_2_raw_record` — the `RawRecord` the adapter's `parse()` wraps it in (adds `source_key`, `bronze_record_id`, hashed `account_identifier`, etc.)
3. `stage_3_bronze_row` — the row as actually persisted to Bronze Parquet (adds `ingestion_id`, `parser_version`, reconciliation/statement-period columns)
4. `stage_4_silver_transaction` — the canonical row in Silver's `transactions` table, after account resolution and two-tier matching (`silver_transaction_id` minted)
5. `stage_5_silver_account_ledger_row` — the corresponding row in Silver's `account_ledger` table, if that source_type captures a balance anchor

Plus whole-file facts that apply to the statement as a whole rather than
one transaction: `account_resolution` (how the file's account was mapped),
and `file_level_facts` (the reconciliation self-check and statement period,
if the source has them — see CLAUDE.md gotchas #6 and #14).

Fields that vary on every real run (wall-clock timestamps, tmp-dir-backed
paths) are replaced with a fixed placeholder string so the file is
byte-stable; everything else — every hash, id, and amount — is the real,
reproducible output of the fixture text below `raw_pdf_text`.

## Regenerating

Each trace is produced and verified by a test in `tests/e2e/test_adapter_trace.py`.
To refresh one after an intentional pipeline change:

```bash
rm docs/adapter_traces/<source_type>.json
uv run pytest tests/e2e/test_adapter_trace.py -k <source_type> -v
```

The first run regenerates the file and fails on purpose (so you review the
diff before trusting it); the second run should pass.

## Coverage

| source_type  | trace file        | notable in this one |
|--------------|--------------------|----------------------|
| `monzo-flex` | `monzo-flex.json`  | no account identifier at all (source_type-wide fallback); direct-read balance; a real page-boundary description scramble |
| `amex`       | `amex.json`        | real per-card identifier (hashed); balance is *derived* by rolling forward from a printed anchor, not read directly; two visually distinct credit ("CR") markers |

To add another adapter, copy `TestMonzoFlexTrace` (or `TestAmexTrace`, if
the adapter overrides `_extract_text` or otherwise needs real PDF bytes
rather than a plain-text stub — see its docstring) in
`tests/e2e/test_adapter_trace.py`, point it at that adapter's own
`SAMPLE_TEXT` fixture (already exists in most `tests/unit/adapters/test_*.py`
files), and pick 3-5 transactions that cover its interesting cases — a
plain debit, a plain credit, and whatever edge case that adapter's own
docstring calls out.

If a fixture needs a real PDF (built with `fitz`, as `TestAmexTrace` does),
note that `Document.tobytes()` stamps a fresh random trailer `/ID` on every
call even for byte-identical content — normalize it the same way
`_deterministic_pdf_bytes()` does, or the fixture's own file hash (and every
id derived from it) won't be reproducible between runs.
